# Registro de Decisiones de Arquitectura (ADR)

Este documento detalla las decisiones técnicas adoptadas en la implementación de **Solucion_entrega**, sus alternativas evaluadas y las razones de su elección.

| # | Decisión | Alternativas Evaluadas | Justificación Técnica |
|---|---|---|---|
| **1** | **Parseo con código determinista** (`openpyxl`, `pdfplumber`, regex) | Usar un LLM para extraer tablas y campos | Los documentos de la prueba mantienen una estructura estandarizada. El código tradicional es 100% exacto, instantáneo, reproducible, sin costo por token y testeable mediante pruebas unitarias. |
| **2** | **IA quirúrgica solo para resumen ejecutivo** | Clasificación por IA o consultas en lenguaje natural | Las cifras numéricas son calculadas por `pandas`. El LLM recibe exclusivamente un JSON de métricas exactas con la instrucción de no inventar datos. Esto elimina el riesgo de alucinaciones numéricas. |
| **3** | **Fallback determinista ante fallos de IA** | Interrumpir la ejecución si la API de IA falla | La IA representa un valor agregado y no un punto único de falla (*Single Point of Failure*). Si la API no tiene saldo, no hay internet o no hay API key, se genera una síntesis determinista con las cifras exactas. |
| **4** | **`row_hash` como Primary Key** | Deduplicar únicamente por nombre de archivo o correo | Se calcula un hash SHA-256 de los campos de negocio (`fecha|cliente|categoria|valor|estado|referencia`). Si el mismo registro llega en correos o archivos distintos, la base de datos previene duplicados a nivel de fila. |
| **5** | **Conteo con Opción A** | `upsert(ignore_duplicates=True)` a ciegas | PostgREST no reporta la cantidad de filas ignoradas al usar `ignore_duplicates`. Consultar previamente en bloques los `row_hash` existentes permite reportar con total exactitud cuántas filas son nuevas y cuántas duplicadas. |
| **6** | **Marcar incidencias (`issues`) en vez de descartar** | Descartar filas con datos incompletos | No se pierde información operacional. Las filas con valores faltantes o negativos se guardan marcadas para que el humano o auditor pueda revisarlas en el dashboard. |
| **7** | **Persistencia en Supabase (PostgreSQL en la nube)** | SQLite local o Google Sheets | En plataformas de despliegue gratuitas como GitHub Actions y Streamlit Community Cloud, el disco local es efímero. Supabase permite que el job de ingesta y el dashboard compartan la misma base de datos sin servidores propios. |
| **8** | **Mínimo privilegio con Row Level Security (RLS)** | Usar la misma clave `service_role` en todos los componentes | El pipeline de ingesta usa `SUPABASE_SERVICE_KEY` (escritura). El dashboard público en Streamlit usa exclusivamente `SUPABASE_ANON_KEY`, restringido por RLS a lecturas `SELECT` sobre `records`, `summaries` y archivos en `processed_items`. |
| **9** | **Cron diurno en horario laboral (8:00 a 18:00 Bogotá)** | Cron 24/7 cada pocos minutos | Ejecutar de noche o fines de semana consume minutos gratuitos de GitHub Actions innecesariamente. Un correo recibido en la noche se procesa automáticamente a primera hora (8:00 a. m.). |
| **10** | **Soporte dual de IA (Google Gemini + Anthropic Claude)** | Proveedor único | Permite alternar fácilmente según la disponibilidad de credenciales (`GOOGLE_API_KEY` o `ANTHROPIC_API_KEY`), con detección automática de endpoints de AI Studio y Vertex AI. |
| **11** | **Logging dual y manejo de errores resiliente** | Solo imprimir en consola con `print()` | `setup_logging()` envía registros estructurados a consola y a `data/pipeline.log`. Las fallas en archivos corruptos o credenciales IMAP se atrapan limpiamente y se auditan en Supabase. |
| **12** | **Alertas proactivas en Dashboard** | Solo mostrar tablas pasivas | El dashboard incluye banners visuales (`st.error` ante archivos no legibles y `st.warning` ante registros con inconsistencias) para advertir inmediatamente al operador. |
